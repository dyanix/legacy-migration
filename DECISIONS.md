# DECISIONS.md

Engineering decisions, their rationale, and known limitations for the
AI-assisted legacy migration platform.

This document exists because the scenario that motivates this project is a
prior migration that "applied a status code mapping inconsistently, silently
corrupting records." The defence against that is not a better model — it is a
written record of what was decided, by whom, and why.

---

## 1. Confidence threshold

**`CONFIDENCE_THRESHOLD = 0.80`** (set in `.env`, read by `ai_mapper`,
`review_ui`, and `rule_generator`).

Mappings scoring **≥ 0.80** are auto-approved. Anything **below** routes to the
Flask review UI and cannot proceed until a human records a decision *and* a
non-empty note. `rule_generator.check_blocking_violations()` enforces this and
exits non-zero if any rule violates it, so the gate cannot be bypassed by
running the pipeline again.

**Why 0.80 rather than higher or lower.** The threshold was chosen to sit above
the band where the model's own reasoning shows genuine ambiguity. In this run,
every mapping the model scored below 0.80 had a specific, articulable reason —
an undocumented code value, a missing lookup table, a type that contradicted
the observed data. Nothing below the line was a false alarm in the sense of
"the model was just being modest."

Raising it to 0.90 would have pulled in mappings like `TRIM(fst_nm)` where
there is nothing for a human to add. Lowering it to 0.70 would have
auto-approved `enc_log.pmt_st_cd` (0.55) and `dx_codes.dx_cd` (0.75) — the two
mappings where human review prevented irreversible semantic loss (§3).

**Empirically, on this dataset:** 32 mappings, 13 gated (41%), 19 auto-approved.
A 41% review rate is high, and appropriate for a first migration of clinical
data where no target schema had been agreed. It is not a steady-state number.

**The threshold is a routing decision, not a correctness claim.** See §3.4 —
two mappings the model scored at 0.97 and 0.85 were surfaced for review only
because of a parsing bug, and one auto-approved mapping later required
correction. High confidence is a statement about the model's certainty, not
about whether the mapping is right.

## 2. Sensitive data acknowledgment

**This dataset is synthetic.** All patient names, dates of birth, diagnoses and
encounter records are generated by Faker (`db/02_seed.py`). No real patient
data was used at any point.

**It is nonetheless shaped like PHI**, and has been handled as such, because a
platform that only behaves correctly on synthetic data is not a platform.

### Automated detection

`agents/schema_profiler.py` flags sensitive columns by two independent methods —
column-name pattern and sample-value pattern — and writes a `pii_summary` block
into `audit/schema_profile.json`. It flags **12 of 28 source columns**:

| Column | Category |
|---|---|
| `patient_records.fst_nm`, `patient_records.lst_nm` | person_name |
| `patient_records.dob` | date_of_birth |
| `patient_records.admit_dt`, `patient_records.discharge_dt` | service_date_phi |
| `enc_log.enc_dt` | service_date_phi |
| `dx_codes.dx_id`, `dx_codes.dx_cd`, `dx_codes.dx_desc` | diagnosis_phi |
| `prv_tbl.prv_nm` | person_name |
| `prv_tbl.npi` | provider_identifier |
| `dept_master.dept_nm` | person_name |

These flags propagate into `docs/data_dictionary.md`, which carries a
**Sensitive column inventory** section so that whoever grants access to the
migrated warehouse can see what they are granting access to.

**The detector deliberately over-flags.** `dept_master.dept_nm` is a department
name, not a person's name — it matches the `_nm$` suffix pattern. `dx_codes.dx_id`
is a surrogate key, not a diagnosis. Both are false positives. This is the
correct direction to err for PHI: a reviewer dismissing an over-flag costs
minutes, an unflagged diagnosis column costs a breach. It is pattern matching,
not classification, and is documented as such in the profiler's own comments.

**Under HIPAA's identifier list**, names, dates more specific than year that
relate to an individual (admission, discharge, birth), and provider identifiers
would all be in scope. Diagnosis codes are not identifiers in themselves but
are the clinical payload the identifiers protect.

### Regulatory constraints — current state

The scenario states that data-at-rest encryption, access controls, and audit
obligations apply. The target is **Snowflake** (`MIGRATION_TARGET.PUBLIC`).

| Control | State |
|---|---|
| Encryption at rest | **Yes.** Snowflake encrypts all stored data with AES-256 by default. Not optional, no configuration required. |
| Encryption in transit | **Yes.** The Python connector uses TLS to `*.snowflakecomputing.com`; there is no unencrypted mode. |
| Access control | **Available, not applied.** Snowflake provides role-based access control and column-level masking policies. This project connects as `ACCOUNTADMIN` and applies no restriction to the 12 flagged columns. |
| Credential management | **Development-grade.** The Snowflake password is a literal in `.env` (gitignored) and in `~/.dbt/profiles.yml` (outside the repo, per dbt convention). |
| Source connection | **Not encrypted.** MySQL in Docker over plaintext `localhost:3307`. Choosing a managed warehouse did not change this — only the target moved. |
| Audit logging | **Implemented.** See §4. |
| Data minimisation | **Not applied.** All columns migrate, including all 12 flagged. |

Two controls are satisfied because they are properties of the platform rather
than things this codebase implements. That is a large part of why a managed
warehouse was chosen over a file-based target: the security floor should not
depend on the migration tool getting it right.

It did not resolve access control, and it made credential handling matter more
rather than less. A leaked local file path exposes a file; a leaked
`ACCOUNTADMIN` password exposes a cloud account with billing attached.

### What production would require

- **A least-privilege role.** Running the migration as `ACCOUNTADMIN` is
  convenient and wrong. A dedicated `MIGRATION_ROLE` with rights only on
  `MIGRATION_TARGET`, plus a separate read-only role for analysts, is the
  minimum.
- **Key-pair authentication** instead of a password in `.env`, or secrets from a
  managed store. Snowflake supports key-pair natively.
- **TLS on the source connection**, which the move to Snowflake did not address.
- Column-level access control on the 12 flagged columns, and masking in any
  non-production copy.
- Retention and deletion policy — this platform copies data and never removes it.
- **`audit/schema_profile.json` and `audit/ai_mappings.json` would need review
  before leaving a controlled environment.** The profiler captures
  `sample_values` from every column, and `ai_mapper` embeds those values into
  `prompt_text`. With real patient data both files would contain PHI. They are
  committed here only because the data is synthetic.
- **Sending column samples to a third-party LLM is itself a disclosure.** With
  real PHI this would require a BAA with the model provider, or a
  locally-hosted model, or profiling that transmits only metadata and never
  values. The current design sends values deliberately — they are what let the
  model catch `pat_st_cd`'s junk codes — so this is a real tradeoff, not an
  oversight.

## 3. Human review outcomes

13 of 32 mappings were gated and reviewed. Every decision carries a note; all
are recorded in `audit/reviewed_mappings.json` and in the audit log.

| Mapping | Conf. | Decision | Rationale (abridged) |
|---|---|---|---|
| `dept_master.dept_id` | 0.75 | approve | Empty-string sample was a profiler display artifact, not source data. |
| `dept_master.active_flg` | 0.75 | approve | Y/N/else-NULL correct; refuses to guess on unobserved values. |
| `dx_codes.dx_cd` | 0.75 | **override** | Preserved `TBD` instead of nulling it — see §3.1. |
| `dx_codes.dx_desc` | 0.40 | **override** | Removed `CAST(... AS VARCHAR(255))`; silently truncates TEXT. |
| `enc_log.enc_typ_cd` | 0.75 | **override** | Kept raw codes; `TC` ambiguous — see §3.2. |
| `enc_log.pmt_st_cd` | 0.55 | **override** | Kept raw codes; `P` = Paid or Pending — see §3.2. |
| `enc_log.notes_txt` | 0.55 | **override** | Rule held two expressions; the TRIM would have been dropped. |
| `patient_records.pat_st_cd` | 0.55 | approve | Codes preserved raw; `X` (130 rows) has no confirmed meaning. |
| `patient_records.lst_nm` | 0.00 | approve | Score was a parse bug — see §3.4. `INITCAP` must not be applied. |
| `patient_records.created_ts` | 0.60 | **override** | Column was never malformed — see §3.3. |
| `patient_records.updated_ts` | 0.55 | approve | 100% NULL in source; migrated as-is, not defaulted. |
| `prv_tbl.prv_nm` | 0.00 | approve | Parse bug; name kept whole rather than split by regex. |
| `prv_tbl.dept_id` | 0.55 | **override** | Renamed to `dept_id` to match the PK — see §3.5. |

### 3.1 Preserving `TBD` rather than nulling it

The model proposed mapping the placeholder `TBD` (~11% of `dx_codes` rows) to
NULL. The source already has 10.16% true NULLs.

Nulling `TBD` would merge **"diagnosis pending"** with **"diagnosis absent"**.
Those are different clinical states, and once merged the distinction cannot be
recovered from the target. Rule changed to `UPPER(TRIM(dx_cd))`.

The model flagged this itself and asked for a business decision — correct
behaviour, and exactly what the gate is for.

### 3.2 Codes preserved rather than expanded to labels

Two columns were proposed with `CASE` expressions expanding single-character
codes into English labels. Both were overridden to `TRIM(UPPER(...))`.

- `enc_typ_cd`: `TC` could be Telehealth Consult, Transitional Care, or Trauma
  Center. No lookup table exists to confirm which.
- `pmt_st_cd`: `P` could be Paid or Pending. On billing data that is a material
  difference. The `?` value (486 rows) would have been merged into the `ELSE`
  branch, losing the distinction between an explicit `?` and an unrecognised code.

Both rules also ended `ELSE 'UNKNOWN'`, which would silently swallow any code
introduced later.

**General principle applied throughout: a migration should not be the place a
guess becomes permanent.** Expanding codes to labels is a semantic decision that
belongs in a reviewed lookup table, not in a transformation rule inferred from
column names. Both columns are named `_code`; preserving codes also makes the
name honest.

### 3.3 `created_ts` — the AI reasoned carefully about a bug that wasn't in the data

The model produced three paragraphs analysing an apparently malformed value,
`atetime.datetime(2026, 8, 1, ...)` — noting the missing leading `d`, inferring
a truncation artifact, and proposing a `REGEXP_REPLACE` parser.

That parser produced **NULL for all 12,000 rows**. The validator's new-nulls
hard failure caught it and blocked the pipeline.

Querying the source directly showed `created_ts` is an ordinary MySQL
`TIMESTAMP`. The `datetime.datetime(...)` string was never in the database —
it is **Python's `repr()` of a datetime object**, introduced by
`schema_profiler` when serialising sample values. The model reasoned correctly
about the input it was given; the input was wrong.

Rule corrected to `CAST(created_ts AS DATETIME)`; the column now loads 12,000
rows with zero nulls.

**Three things this demonstrates, and they are the reason it is written up at
length:**

1. The validator's hard-failure gate works on a real failure, not a contrived one.
2. Model output quality is bounded by input quality. The most consequential bug
   in this run was in the profiler, not the LLM.
3. `schema_profiler` still serialises datetimes via `repr()`. This affects
   `admit_dt`, `discharge_dt`, `enc_dt`, and `updated_ts` as well. **Open — see §6.**

### 3.4 Confidence 0.00 was a parsing failure, not a model judgement

`patient_records.lst_nm` and `prv_tbl.prv_nm` both displayed **confidence 0.00**.
Their `edge_cases` fields end with a leaked fragment:

```
... "Names with suffixes..."]  <parameter name="confidence">0.97
... "Cardinality of 40..."]    <parameter name="confidence">0.85
```

The model's actual scores were 0.97 and 0.85. `with_structured_output` folded
the `confidence` field into the `edge_cases` array, so the Pydantic
`default=0.0` applied.

**The failure mode was safe by design.** `ColumnMapping` defaults `confidence`
to `0.0` specifically so that a malformed or truncated response is forced into
human review rather than silently trusted. Both mappings surfaced for review and
were approved on merit.

This is why the review UI also allows correcting **auto-approved** mappings
(§5.3): a confidence score is a claim about the model's certainty, and can be
wrong in either direction.

### 3.5 Naming consistency chosen over the model's preference

The model proposed `prv_tbl.dept_id → department_id` while
`dept_master.dept_id → dept_id`. Both defensible in isolation; together they
break the FK relationship.

`agents/generate_dbt_models.py` detects foreign keys by exact column-name match,
so `department_id` would have silently dropped the `prv_tbl → dept_master`
relationship test — validation coverage lost with no error. Overridden to
`dept_id`.

## 4. Audit trail

`audit/migration_audit_log.json`, written solely by the orchestrator.
**465 entries** at time of writing, accumulated across runs:

| Status | Count |
|---|---|
| `ai_suggestion` | 224 |
| `auto_approved` | 114 |
| `human_decision` | 78 |
| `ran` / `skipped` | 27 / 19 |
| `paused` / `blocked` / `failed` | 1 / 1 / 1 |

### Immutability is tamper-evidence

Any file can be edited. Each entry therefore carries `prev_hash` and
`entry_hash`, forming a SHA-256 chain over its own content plus the previous
entry's hash. Editing a past decision, or deleting an entry, breaks every hash
after it.

```bash
python -c "from workflow.langgraph_orchestrator import verify_audit_log; print(verify_audit_log())"
```

Verified against five attacks: editing an `override_note`, flipping
`human_reviewed`, raising a confidence score, deleting an entry, and backdating
a timestamp. All five are detected, with the offending entry number reported.

**Why one writer.** All eight nodes could append independently, but concurrent
writers on a single file make an intact chain impossible to guarantee. The
orchestrator appends as each node returns.

### Prompt ID traceability

Every AI suggestion is traceable end to end by a single identifier:

```
ai_mapper generates prompt_id
  → audit/ai_mappings.json
  → audit/reviewed_mappings.json  (alongside the human decision)
  → audit/transformation_rules.json
  → audit/migration_audit_log.json  (ai_suggestion + human_decision entries)
  → docs/data_dictionary.md  (AI provenance table)
  → LangFuse trace metadata
```

Given any column in the migrated warehouse, that chain answers: what was the
model asked, what did it propose, how confident was it, did a human intervene,
what did they change, and why.

### Revision history

The review UI originally offered no way to revise a decision after export —
discovered when `created_ts` needed correction. Fixed, with the constraint that
**revising appends rather than overwrites**: the superseded decision keeps its
rule, note, and timestamp in a `revision_history` list. A reviewer changing
their mind is normal; a reviewer silently replacing a prior decision is what an
audit log exists to prevent.

`ai_original` also snapshots the model's proposal on first human contact, so
the "before" survives any number of revisions.

## 5. Architectural decisions

### 5.1 Great Expectations gates; dbt advises

Both validation layers run, but only GE and the reconciliation report can block.
`validator.py` computes `success` purely from `all_hard_failures`, which only
reconciliation populates.

dbt requires its own adapter, profile, and credentials outside the repo. Making
the pipeline's pass/fail depend on optional external configuration would mean a
correctly-migrated dataset failing because someone hadn't written a
`profiles.yml`. dbt records its result in the report and never gates.

Only two conditions produce a hard failure: a target row count that disagrees
with what the executor loaded, and a column that was never null in source
acquiring nulls in target. Both are cheap, unambiguous, and catch the failure
mode from the motivating scenario. Everything else is informational, because
transformed values are *supposed* to differ from source.

### 5.2 dbt models are generated, never hand-written

`agents/generate_dbt_models.py` builds `stg_*.sql` and `schema.yml` from
`audit/transformation_rules.json` at validation time.

The first hand-written set selected `department_id` when the target had
`dept_id`, and `patient_status` when it had `patient_status_code`. Every model
failed to compile. Target column names come from
`ai_mapper → human_review_gate → rule_generator`, and `rule_generator` re-runs
every execution — so a hand-written model encodes a snapshot that rots on the
next mapping change.

The generator also **verifies each candidate key against the migrated data**
before emitting a test. An early version inferred keys from column names and
picked `encounter_date` as a primary key. A validation layer that cries wolf
gets ignored, which is worse than no validation layer.

### 5.3 The confidence gate is not a correctness boundary

Auto-approved mappings remain correctable in the review UI. §3.4 is the reason:
a score of 0.97 was rendered as 0.00 by a parse bug, and the reverse is equally
possible. Corrections to auto-approved mappings record as human decisions with
notes, identically to gated ones.

### 5.4 Facts are deterministic; only prose is generated

`doc_generator` assembles lineage, transformation logic, confidence, and human
overrides directly from the JSON artifacts. The LLM writes table-level
overviews only, and its system prompt forbids inventing clinical semantics,
code meanings, or units.

Column descriptions reuse `inferred_meaning` from the approved mappings rather
than being regenerated. That costs nothing, and — more importantly — a fresh
description could contradict the mapping a reviewer signed off on.

### 5.5 The target sits behind an interface

`TargetWriter` defines connect / create / load / read / count, and
`migration_executor` and `validator` speak only to that interface. Snowflake is
the target; nothing above the writer knows which warehouse it is talking to.

This was not decorative. Moving from a file-based development target to
Snowflake changed no pipeline code — only `TARGET_BACKEND`, credentials, and
the writer itself. It also localised the failures that move produced: identifier
casing, schema-qualified lookups, and bulk-load strategy were all wrong in the
first Snowflake implementation, and all four bugs lived inside one class rather
than being scattered through the executor and validator.

## 6. Known limitations

Open items, stated rather than hidden.

**`schema_profiler` serialises datetimes via `repr()`.** Root cause of §3.3.
Still affects `admit_dt`, `discharge_dt`, `enc_dt`, `updated_ts`. Fix is to
serialise with `.isoformat()` in `profile_column`'s sample capture.

**Incremental loads use `>` rather than `>=`.** Rows sharing the maximum
watermark timestamp are skipped permanently. With second-granularity timestamps
and 25,000 rows this window is realistic. Mitigation would be `>=` plus dedupe
on the primary key, or backing the stored watermark off by a safety interval.

**Incremental loads have no upsert.** A row *updated* in source is inserted as a
second copy rather than replacing the original. Snowflake does not enforce
primary key constraints — they are metadata only — so nothing at the target
prevents it either. Not yet triggered, because `enc_log` extracts 0 rows on an
incremental run.

**All target columns are created VARCHAR.** The transformation rules carry no
target type, so nothing types the Snowflake columns. Dates, numerics and
booleans all land as text. This was invisible on a file-based target and is a
real limitation on a warehouse: downstream consumers cannot sort, range-filter
or aggregate without casting. Fixing it means extending the rule schema with a
target type, which is a mapping-layer change rather than a writer change.

**The migration runs as `ACCOUNTADMIN`.** See §2.

**dbt materialises its views into the migrated schema.**
`MIGRATION_TARGET.PUBLIC` holds 5 tables plus 6 dbt views. Unlike a single-file
target, Snowflake can separate them — pointing dbt's `schema:` at a dedicated
schema in `profiles.yml` would resolve it.

**`patient_records` can never load incrementally.** Its only watermark
candidate, `updated_ts`, is 100% NULL in source.

**Configuration that lives in a command diverges from configuration in `.env`.**
Three separate failures in this project traced to a value being set on one code
path but not another: the LLM key worked in `ai_mapper` but not
`doc_generator`; `LLM_MODEL` defaulted differently in each of those two nodes;
and `DBT_TARGET_SCHEMA` worked when passed on the command line but not when the
orchestrator regenerated the dbt models itself, producing
`Schema 'MIGRATION_TARGET.MAIN' does not exist`. Each time the fix was to move
the value into `.env`, where every path reads it. The failure mode is
consistent and worth naming: a setting scoped to one invocation surfaces later
as a downstream error rather than as a configuration error.

**`rule_generator` output requires sanitisation at execution time.** Rules have
arrived containing trailing SQL comments, embedded column aliases, and fragments
of complete `SELECT` statements (`... AS patient_id FROM enc_log`).
`migration_executor` repairs all three. The repairs are logged, but a reviewer
approving a rule in the UI sees text that differs from what executes — the
approved *logic* is unchanged, only its dialect-specific spelling.

**dbt materialises views into the migration target.** `migration_target.db`
contains 11 objects: 5 migrated tables plus 6 dbt views. Validation artifacts
sharing a schema with migrated data would not be acceptable in production;
pointing dbt at a separate database file would resolve it.

**`.env` and `docker-compose.yml` carry development credentials.** See §2.

## 7. What this platform does not do

Stated so nobody infers capability from silence.

- **No rollback.** A failed migration leaves the target in whatever state it
  reached. `--full-reload` rebuilds from scratch, which is recovery, not
  rollback. Recovery is per-table and not transactional across tables.
- **No schema evolution.** New source columns require re-running `ai_mapper`
  and the review gate.
- **No value-level reconciliation.** Row counts and null rates are compared;
  individual values are not, because transformed values are expected to differ.
  A rule that maps every `sex_cd` to `'Male'` would pass validation. Correctness
  of transformation *logic* is caught at the review gate, not by the validator.
- **No scheduling.** Runs are manual.
