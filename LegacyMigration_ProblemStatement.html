AI-Assisted Legacy Data Migration
Platform

Build an AI-infused migration platform where LangChain agents understand schema semantics and generate auditable transformation rules, while LangGraph orchestrates the full pipeline with human-in-the-loop confidence gating at every high-risk decision.

★★★★☆ Advanced Data Migration LangChain Agents LangGraph Human-in-the-Loop
01 Problem Statement

Legacy database migrations are notoriously expensive, slow, and error-prone. The typical failure pattern is not technical — it is semantic. Engineers can move bytes reliably. What they cannot do automatically is understand what those bytes mean across two different schema designs.

Schema mapping is manual — a large database can take weeks to document correctly. Business rules are buried in application code, not in the schema itself. Column semantics are undocumented: a field like status INT could mean anything. Data type mismatches are discovered only after the move, during validation. Transformation logic is inconsistently applied, and migration documentation is written after the fact, if at all.

📋 Project Scenario

Your team has been given access to a legacy relational database (MySQL or PostgreSQL) with minimal inline documentation. The database has accumulated years of organic growth: inconsistently named columns, undocumented status codes, implicit business rules, and zero column-level comments. A previous manual migration attempt applied a status code mapping inconsistently, silently corrupting records. The business now requires that every transformation rule be documented, reviewed, and traceable before any data moves. Regulatory constraints — data-at-rest encryption, access controls, audit obligations — apply depending on data domain and must be acknowledged in your DECISIONS.md.

🎯 Your Mission

Build an AI migration platform where LangChain agents assist with schema understanding, transformation rule generation, and documentation — while LangGraph orchestrates the end-to-end workflow with human-in-the-loop checkpoints at every high-risk decision. The platform must be fully auditable, reproducible, and safe.

05 Recommended Architecture

The following describes the recommended high-level architecture. You may adapt it, but all mandatory components must be present and demonstrably integrated.

1
Source Layer — Legacy OLTP Database
A MySQL or PostgreSQL database representing the legacy system. Must contain at minimum 5 tables with varied column naming conventions, at least one undocumented status-code column, nullable FK relationships, and realistic data volume for profiling (10,000+ rows per primary table).
2
Schema Profiling Layer — Python + SQLAlchemy
A profiling module that introspects the source database via SQLAlchemy reflection — extracting table names, column names, data types, null rates, cardinality, value distributions, and FK graphs. Profiling output is serialized as a structured JSON document that feeds all downstream AI agents.
3
AI Orchestration Layer — LangGraph + LangChain
The core migration graph built with LangGraph. Nodes represent pipeline stages: schema profiling → AI mapping → human review gate → rule generation → ETL execution → validation → documentation. LangChain agents power the inference and generation nodes. The graph handles conditional routing, retry-on-failure, and audit logging at every step.
4
Human Review Interface
When the LangGraph workflow pauses at the human review gate, a review interface (CLI, simple web UI, or structured JSON queue) presents flagged low-confidence mappings for a human operator. Approve, reject, or override decisions are captured and written to the audit log before the pipeline resumes.
5
Validation Layer — Great Expectations + dbt
Great Expectations suites run at three checkpoints: source baseline (pre-migration), post-extraction, and post-load (target). dbt models execute post-migration tests covering row counts, null rates, FK integrity, and business rule checks. A reconciliation report compares source vs target for every migrated table.
6
Observability — LangFuse
Every LLM call, agent decision, confidence score, and human override in the workflow is traced to LangFuse. Traces include prompt input, model output, latency, and any human annotation. The LangFuse dashboard must show a per-agent trace view covering the full migration run and be submitted as part of your deliverables.
06 LangGraph Migration Workflow

The migration orchestrator must implement the following node sequence. Each node is a discrete LangGraph state with defined inputs, outputs, and failure handling. Nodes must execute in order unless the conditional routing logic routes to the human review queue.

🔍
schema_profiler
Introspects source DB — outputs table/column stats, sample values, null rates, cardinality, and FK graph. This snapshot is the ground truth for all downstream AI decisions and the baseline for Great Expectations validation suites.
🧠
ai_mapper
LangChain agent receives the schema profile and generates target schema mappings with a confidence score (0.0–1.0) and reasoning trace per column. Every mapping is stored alongside the prompt ID that produced it, for full traceability.
🚦
human_review_gate
Conditional node — routes any mapping with confidence < 0.80 to a human review queue. Pipeline pauses until a human approves, rejects, or overrides each flagged mapping. All decisions are logged and versioned before the pipeline resumes. No mapping bypasses this gate.
📋
rule_generator
Generates transformation rules in the standard JSON schema from approved mappings using a LangChain agent. Every rule must be traceable to the LLM prompt that generated it and the human approval that cleared it for execution.
⚙️
migration_executor
Executes extraction, transformation, and load to the target cloud warehouse using the approved rule set. Includes Python-based retry with exponential backoff on transient failures. Airflow DAG integration is available as an optional scheduling extension.
✅
validator
Runs Great Expectations suites post-extraction and post-load. Generates a reconciliation report comparing row counts, null rates, and value distributions between source and target for every migrated table. Failures block pipeline completion.
📖
doc_generator
LangChain generates a complete target data dictionary from approved mappings and transformation rules — including column definitions, data lineage, transformation logic applied, and any human overrides recorded. This becomes the canonical documentation for the migrated schema.
07 Transformation Rule Schema

All AI-generated transformation rules must conform to the following JSON structure. This ensures consistency across teams and makes every rule fully auditable and replayable.

{ "source_column": "pat_st_cd", "target_column": "patient_status", "logic": "CASE WHEN src = 'A' THEN 'Active' WHEN src = 'D' THEN 'Discharged' ELSE NULL END", "null_handling": "Map to NULL; flag in reconciliation report.", "edge_cases": ["Unknown codes default to NULL", "Trim whitespace before mapping"], "confidence": 0.84, "prompt_id": "prompt-uuid-abc123", "human_reviewed": false, "override_note": null }
🚫 Required — Blocks Pipeline

Any rule with confidence < 0.80 must have human_reviewed = true and a non-null override_note before it is passed to migration_executor. Rules without this are treated as unapproved and block the pipeline.

08 Prompting Discipline
✅ Complete Prompt Example

A well-formed schema inference prompt includes schema context, sample values, and an explicit request for confidence and reasoning:

You are a data migration assistant. Given the following column metadata, infer the semantic meaning, generate a transformation rule, and return a confidence score with reasoning. Column: pat_st_cd Type: VARCHAR(2) Sample values: ["A", "D", "I", "S", "D", "A", "A"] Null rate: 0.02 Table: patient_records Related columns: pat_id (PK), admit_dt, discharge_dt Return JSON with fields: inferred_meaning, transformation_rule, null_handling, edge_cases, confidence (0.0–1.0), reasoning. Do not guess on values with no clear pattern — flag those for human review.

Other strong prompt patterns:

💬
"What column semantics can you infer from pat_st_cd with sample values ['A','D','I','S']?"
Anchors the agent on concrete sample data rather than relying solely on naming conventions.
💬
"Generate a transformation rule for this approved mapping — include edge cases, null handling, and a confidence score."
Forces all required rule schema fields to be populated in a single structured output call.
💬
"Which mappings should be flagged for human review, and what is the minimum confidence threshold?"
Surfaces ambiguity explicitly rather than letting the model silently commit to a low-confidence guess.
💬
"How should the LangGraph workflow handle a partial migration failure — retry from checkpoint or full rollback?"
Elicits failure-mode reasoning that feeds directly into your DECISIONS.md and rollback runbook.

Weak prompts — red flags that will fail evaluation:

✗ Disqualifying Prompt Patterns

"Migrate all the tables." — No schema understanding step, no confidence gating.
"Map source to target automatically." — No human review, no audit trail.
"Fix the data quality issues." — No profiling step, no issue classification.

10 Failure Modes & Anti-Patterns

The following are disqualifying anti-patterns. Any submission exhibiting these will not pass evaluation.

✗
Accepting all AI-generated mappings without a confidence gate
Automation without oversight is the exact failure pattern the platform is built to prevent. Every mapping must pass through the confidence gate.
✗
No audit trail for LLM decisions
Untraceable AI-driven data changes are unacceptable in any regulated environment. Every AI suggestion, confidence score, and human decision must be logged immutably.
✗
Running migration without a pre-migration Great Expectations baseline
No baseline means no rollback reference point if the load fails. The source validation suite must run before any data is moved.
✗
No reconciliation report
Migration declared complete without source-vs-target row count and distribution verification is not a completed migration — it is an unverified data move.
✗
LangGraph workflow with no human-in-the-loop node
A fully automated migration of ambiguous mappings violates the core design requirement of the capstone and will result in automatic disqualification.
⚠️ Where AI Falls Short

True semantic ambiguity: Only a domain expert knows that a given code means 'Discharged' rather than 'Deceased'.  ·  Business rule validation: LLM-generated rules must be verified by the application team before going live.  ·  Performance tuning: Pipeline optimization requires profiling at real data volumes, not synthetic test sets.

13 Evaluation Criteria

Your submission will be evaluated by the FDE programme's DIFY-based automated assessment workflow across the following dimensions:

⚙️
Functional Correctness 35%
Does the pipeline execute end-to-end successfully? Are all 7 LangGraph nodes implemented? Does the confidence gate correctly pause for low-confidence mappings and resume after human review? Do Great Expectations suites run at all three checkpoints?
🔗
Agent Design & Orchestration 25%
Quality of the LangGraph agent graph — state design, node decomposition, conditional routing logic, and transformation rule schema conformance. LangFuse traces must be present and well-structured for every LLM call in the workflow.
📋
Audit Trail & Human-in-the-Loop 20%
Completeness and immutability of the migration audit log. Quality of DECISIONS.md — confidence thresholds justified, human overrides documented with rationale, sensitive data acknowledged. Every AI suggestion traceable to a prompt ID.
📦
Code Quality & Documentation 15%
Project structure, code readability, completeness of README runbook (re-run, rollback, inspect AI decisions), quality of .env.example, and whether dbt models cover all required post-migration validation checks.
✨
Innovation & Bonus Features 5%
Any creative extensions beyond the minimum requirements — e.g., Airflow DAG scheduling, a visual mapping review UI, multi-table dependency resolution, automated PII/sensitive column detection in the profiler, or incremental migration support.
